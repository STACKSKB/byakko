# Capturing official Nia87 feature traffic without a USB capture driver

This note is based on static inspection of `Research/extracted/official-app/resources/app/iot_driver.exe`, `dist/static/js/main_ccea61a6.js`, and `main_dist/main.js`. The helper was not run for this investigation.

## Best available capture point: the official app's localhost RPC

The renderer creates a client for `http://127.0.0.1:3814` at JavaScript string offset ~15,650,025. Its ordinary HID wrapper calls `sendMsg` with a `SendMsg` containing device path, 64-byte `msg`, checksum type, and dongle type (~15,650,700–15,653,500), then calls `readMsg` and converts `ResRead.msg` to bytes. The generated client binds the unary endpoints `/driver.DriverGrpc/sendMsg` and `/driver.DriverGrpc/readMsg` around offsets 15,480,022 and 15,523,500. This is the app-to-helper boundary. It records **the commands actually chosen by the official UI**, including full matrix writes, without touching a kernel driver.

For a controlled UI change, capture only requests to those two localhost endpoints and retain request and response bodies with timestamps. The `SendMsg` body tells us the command bytes and checksum mode; the associated `readMsg` reply gives the data returned to the app. This boundary is before the helper's checksum handling. Full matrix writes pass checksum mode `NONE` and already contain their explicit checksum byte, so their `msg` should be the feature payload. Simple-key writes pass `BIT7`; the helper supplies payload byte 7, using the checksum independently confirmed by the identity reads. A capture should distinguish these two cases rather than treating all `msg` bytes as final HID bytes.

The app is Electron with `nodeIntegration: true` and `contextIsolation: false` (`main_dist/main.js` near offset 385,132). It opens DevTools automatically only when unpackaged, but does not set `devTools: false`. If DevTools can be opened in the packaged app, its Network panel can filter `127.0.0.1:3814` and preserve the traffic for one controlled action. A more repeatable option is to restart Electron with its documented `--remote-debugging-port=...` switch, attach a local Chrome DevTools Protocol client, and collect request bodies and response bodies for the two RPC paths. Electron documents the switch in its [command-line reference](https://www.electronjs.org/docs/latest/api/command-line-switches); the [DevTools Protocol Network domain](https://chromedevtools.github.io/devtools-protocol/tot/Network/) documents `getRequestPostData` and `getResponseBody`. Whether this packaged build accepts the switch and exposes complete binary request bodies should be verified with an identity read before relying on a write capture. Keep the debugging port bound to localhost and capture only the local RPCs.

The Windows renderer copies the helper into Electron `userData` under a versioned `iot_driver_*.exe` name and starts it with `shell.openPath`, without arguments (renderer offset ~17,797,050–17,798,900). It first stops matching prior helper processes. Thus a manually launched helper can be replaced when the UI starts, and redirecting the existing process's output is not an easy capture route.

## Why the helper's own text output is weak evidence

The extracted helper is a 32-bit Rust PE with the Windows GUI subsystem (PE optional-header subsystem value 2). Static strings show `HidD_SetFeature`, `HidD_GetFeature`, and `hid_send_feature_report`, confirming user-mode HID calls. They also show `Received data from ...` and `data ===>` around file offsets 5,047,920–5,047,992, immediately followed by the source path `src\dj_dev_api\ble_hid.rs`. Those strings likely concern Bluetooth traffic, not the Nia87 USB feature-report path. Other nearby strings such as `sendddd` and `sender EEERRRRR` look like error diagnostics. I found no `RUST_LOG`, `--log`, `--verbose`, or helper log-file path in the binary or launcher. `tracing-core` appears as a dependency, but that alone does not establish an enabled subscriber or packet logging. Capturing stdout from a separately launched helper might reveal errors, but the static evidence does not support it as a complete feature-report trace.

If USBPcap is already installed, capturing control `SET_REPORT` and `GET_REPORT` traffic for VID `0x3151`/PID `0x4015` would observe the actual USB payload after helper processing. Installing its capture filter is outside the no-driver constraint; it can also require choosing the correct host controller and may interrupt a live session. The localhost RPC route is the first capture to try.
