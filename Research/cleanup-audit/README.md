# AST function similarity audit

Run from the repository root with the cached dependencies (no network):

```powershell
cargo run --offline --manifest-path Research/cleanup-audit/ast/Cargo.toml --quiet -- crates/byakko-cli/src crates/byakko-desktop/src src crates/byakko-core/src crates/byakko-devices/src | Out-File -Encoding utf8 Research/cleanup-audit/results.txt
```

The standalone scanner parses `.rs` files with `syn` and collects free and impl function bodies. It separates functions inside `#[cfg(test)]` modules or impls, `#[test]` functions, and paths under `tests` from production. Classification is lexical: any `cfg` attribute containing the word `test` is marked test, including `cfg(not(test))`, so inspect ambiguous hits. Trait default methods and nested functions are omitted. Its exact comparison keeps identifiers and literals. Its normalized comparison replaces every non-keyword identifier with `IDENT` and every literal with `LITERAL`, but keeps punctuation, grouping, and Rust keywords. It reports identical normalized bodies of at least 120 tokens and identical exact bodies of at least 80 tokens. For near matches, it uses the Dice coefficient over sets of five normalized-token shingles, requiring at least 120 tokens per body, lengths within 70%, and a score of at least 0.70. It prints production and test matches separately. Equal-score results sort by source location for reproducibility. The score is a screening aid, not a measured refactor benefit: normalization erases field, method, and variant distinctions, while shingle sets erase frequency and some order information. Macros are opaque tokens; semantic equivalence is not established. The listed groups were manually checked in source.

The fixture command `cargo run --offline --manifest-path Research/cleanup-audit/ast/Cargo.toml --quiet -- Research/cleanup-audit/fixtures.rs` returned four parsed functions with no errors. `exact_a` and `exact_b` formed the 124-token exact group; they and `renamed` formed the 124-token normalized group. The identical body inside the `#[cfg(test)]` module did not join either production group. `cargo fmt --manifest-path Research/cleanup-audit/ast/Cargo.toml -- --check` passed.

Results in `results.txt` cover 183 files and 1,954 function bodies, with zero parse errors. There is no production exact-body match above the 80-token threshold. The largest normalized exact production pair is `crates/byakko-desktop/src/archive.rs:122` and `crates/byakko-desktop/src/macro_files.rs:293`, each 156 tokens. Both create a bounded one-shot channel, spawn a named blocking file worker, and turn its completion into an Iced task. Their result types, completion messages, worker names, and failure text differ. A small typed file-worker adapter is plausible if those conversions remain explicit; do not suppress the macro export warning that a destination may need checking after worker loss.

The main stream pair is `crates/byakko-desktop/src/audio_stream.rs:36` and `crates/byakko-desktop/src/screen_stream.rs:29` (normalized near score 0.807, 441/400 tokens). Both implement `PREPARING → READY → STREAMING → STOPPED`, a one-slot event channel, frame pacing, and a worker thread. The sampler setup, first-frame behavior, frame period, and terminal failure send differ. In particular, audio uses blocking `send` for `Failed`, while screen uses `try_send`, so a mechanical merge could change whether failure is delivered when a frame is pending. Extracting only lifecycle/state helpers after specifying the desired terminal delivery behavior is the safer candidate. The legacy `src/audio_stream.rs:14` and `src/screen_stream.rs:9` also match (0.786); their relationship to the maintained desktop modules should be checked before any edit, given root compatibility role.

CLI planners `crates/byakko-cli/src/picture.rs:11` and `crates/byakko-cli/src/settings.rs:11` score 0.817 (249/273 tokens). Both require a ready session/editor, compare a backend revision, validate an editable snapshot, and derive a change list. Picture additionally checks `context_revision` and complete advertised colors; settings rejects multiple changes. Their apply functions score 0.751, while macro/picture apply score 0.773. The repeated `submit_and_wait` and success-baseline extraction may support a focused helper. Keep per-feature readiness, selector context, single-field limit, macro import ticket, and transport-accepted versus verified wording in the feature files. A generic planner would hide distinct device semantics for little benefit.

Other production matches merit lower priority: memory backend apply functions (`crates/byakko-devices/src/memory.rs:284,329,370`, 0.806–0.881) share bookkeeping but operate on distinct feature models; root/UI read starters have shared shape but are legacy flow; `crates/byakko-devices/src/macro_labels.rs:94` and `src/macro_labels.rs:84` (0.839) may be legacy duplication worth checking at the compatibility boundary. The highest test matches mostly repeat setup while asserting different invariants; retain those tests unless a fixture can be shared without obscuring each assertion.

This is an audit only. It makes no product changes and does not infer that similarity alone justifies extraction.
